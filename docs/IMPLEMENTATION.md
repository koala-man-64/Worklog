## What was built

- Persistent work items, date-specific planning and actual outcomes, historical daily summaries, reflection, manual ordering, backlog filters, and recoverable archives.
- Notes, checklists, managed attachments with hashes, copyable path references, search, and contextual history.
- Structured roadmap trees with permanent step identities, immutable content revisions, explicit leaf progress, derived parent summaries, retirement, restoration, and reviewed HTML conversion. Original HTML is retained byte for byte and is download-only.
- Scoped local agent credentials, a standard-library HTTP CLI, draft/submitted proposals, evidence, comparison with canonical records, and atomic human approval. Approval and its idempotency receipt share the canonical transaction.
- A single loopback service serving production assets, local browser sessions, Host/Origin/CSRF enforcement, bounded uploads, generated OpenAPI request types, and safe Markdown rendering.
- Source setup, hidden Windows launch/reuse/stop, consistent SQLite backups, portable hashed exports, and offline restoration with original-data preservation.

## Important implementation decisions

SQLite uses foreign keys, a rollback journal, full synchronization, and explicit short transactions. The application validates polymorphic supporting-record ownership inside the same transaction; parents are archived rather than deleted. File bytes live in SQLite, so recovery includes records and files together.

Optimistic concurrency uses per-record revisions and collection revisions for ordering. Mutation history is generated by the server. Stable IDs replace array-index addressing. Reads never create days. The UI pages work records and uses a server-selected neighbor for backlog moves across page boundaries.

Browser drafts persist by dataset identity. Revision advances follow acknowledged local transitions from the draft's actual base; a newer unrelated field cannot promote a stale draft. Revision zero is preserved. Conflicts retain the draft and show the current saved value. Browser storage failures retain in-memory edits and report that the tab must remain open until the server confirms saving.

An offline restore revokes agent credentials, rotates dataset identity, and invalidates process-local browser sessions. Old browser drafts remain stored but are never automatically applied into another dataset. A durable restoration marker prevents startup after an interrupted multi-file replacement. The original main file and sidecars are preserved as hashed recovery evidence, including when the active database is corrupt.

The trusted boundary is the Windows account. Browser session and agent API scopes do not claim to isolate a hostile process running as that same account. No external fonts, remote images, scripts, or imported-resource fetching are needed at runtime.

## Reproducing the checks

Tested on Windows with Python 3.14.3 and Node 24.14.0. A separate source snapshot completed setup with a new Python environment and new frontend dependency installation. Exact dependency versions are in `requirements.lock` and `frontend/package-lock.json`.

Final primary-workspace results: 87 backend tests, 16 frontend unit tests, and 9 real-backend Chromium scenarios passed. Backend/frontend lint and type checks, generated API types, production build, and dependency consistency checks passed. Every browser scenario denies non-local HTTP traffic and asserts that the app made no external requests; settings backup/export and light/dark controls are included. Independent crash probes also terminated a restore process at both replacement boundaries and verified startup refusal, retained evidence, and successful explicit recovery.

```powershell
./scripts/Setup.ps1
./.venv/Scripts/python.exe -m pip check
./.venv/Scripts/python.exe -m pytest -q
./.venv/Scripts/python.exe -m ruff check backend tools
./.venv/Scripts/python.exe -m mypy backend/worklog
./.venv/Scripts/python.exe tools/export_openapi.py
Push-Location frontend
npm.cmd run generate:api
npm.cmd run lint
npm.cmd run typecheck
npm.cmd test
npm.cmd run build
Pop-Location
```

Browser checks require a running instance using disposable test data, never a personal database. The Playwright suite documents the affected workflows in `frontend/e2e/worklog.spec.ts`; use the README's isolated launch instructions before `npm run test:e2e`.

Detailed local-only install and lifecycle receipts are retained under `.local/clean-setup-result*.log`, `.local/clean-setup-result.json`, and `.local/ops-smoke/smoke-result.json`. Generated build outputs, test data, logs, credentials, and dependency folders are excluded from Git.

## Operating limits

Normal use is internet-free after setup. Source installation requires package access and the documented Python/Node prerequisites. Automated backups are local copies; retain a verified copy elsewhere for device-loss recovery. Archives retain content and consume space; permanent purging is intentionally outside this release. A nonfatal Starlette TestClient deprecation warning is present in the pinned test stack; it does not affect the running application.

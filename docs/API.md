# Worklog implementation contract

The discussion API extends the original contract below. See [Discussions and responsibilities](DISCUSSIONS.md) for operating semantics and CLI examples. Generated request contracts are in `openapi.json`.

## Discussions

All discussion writes require `Idempotency-Key`. Authentication selects the actual author; clients cannot supply one. Discussion retry receipts use stable communication identity while existing proposal identity is unchanged.

- `GET /discussions/participants` returns identities, each with its generated `avatar` name (`null` for the person), and the caller. `GET /discussions/avatars` lists every avatar `{name,available}`, a fresh `suggested` draw and the caller's `current` one; `available` is false when another agent with a live credential shows it. An agent's `POST /discussions/avatar {avatar}` changes its own avatar and returns its participant record; an avatar another active agent shows is `409 avatar_in_use`, and the person gets `403`. `GET /discussions` supports `view=all|awaiting|archived`, `q`, repository and context filters, `limit` and `offset`. `POST /discussions` creates a conversation and first message.
- `GET /discussions/{id}` pages immutable messages. `POST /discussions/{id}/messages` replies. Bodies support optional `chatId`, `onBehalfOfRoleId`, and `acknowledgement` with `mode=all|any|any_agent|anyone` and named `targets` where applicable.
- `GET /discussions/messages/{id}` returns a message and its request state, target slots, receipts, allowed target IDs and cancellation/release capabilities. `POST .../acknowledge` accepts explicit `targetIds` (optional only for open audiences); `.../cancel` checks current management authority. Human-only `.../release` requires `reason`.
- Human-only `POST /discussions/{id}/archive` takes `revision` and `archived`. Archived conversations remain replyable; pending requests remain discoverable.
- `GET /discussions/roles` pages context roles. `POST /discussions/roles` creates `{contextType,contextId,label}`. `POST /discussions/roles/{id}/{claim|release|accept|decline|withdraw}` takes `revision`; `offer` adds `successorId` and optional `note`. Human-only `reassign` adds `ownerId` (nullable) and required `reason`.
- `GET /discussions/resume` returns a consistent context snapshot and cursor; `GET /discussions/changes` incrementally reads ordered changes. Cursors bind dataset, context scope and sequence; invalidated cursors return `409 cursor_reset`. Resume/changes have bounded pagination.
- `POST /credentials/{id}/rotate` accepts an optional `label`, revokes replaced credentials and returns a one-time token bound to the same communication identity. Replaying the same mutation redacts that token. Settings includes retained identities and each credential's `agentId`.

Context types are `item`, `roadmap`, and `step`. Acknowledgement target kinds are `agent`, `human`, and `role`; the human ID is `local-user`. Requests are `pending`, `satisfied`, `released_by_human`, or `cancelled`. Role ownership changes atomically with assignment generation. Receipts retain actual actor and generation; reading/replying/handoff is never receipt.

## Original workbench contract

Owner: root; task WORKLOG-BUILD. Local-only, new repository. Root owns database primitives, work/day/context services and API integration. Plans agent owns plans.py, proposals.py and corresponding tests. Frontend agent owns frontend/. Operations agent owns cli.py, recovery.py, scripts/, README.md and corresponding tests. Shared files require parent coordination. No commits by children.

All API routes start /api/v1. camelCase JSON. UUID ids, integer revision; timestamps UTC ISO strings. Date strings YYYY-MM-DD in configured America/Chicago timezone. States are open, doing, blocked, done. Every mutation sends a JSON object (raw uploads excepted), includes revision for existing records, and an Idempotency-Key header for creates/approval. Error: {error:{code,message,fields?}}. Conflict 409. Envelope lists {items:[...],total:n}; objects returned directly. Session bootstrap POST /session/bootstrap body {} and X-Worklog-Bootstrap: 1 returns {csrfToken,today,timezone}; fetch credentials same-origin, X-CSRF-Token on cookie writes. Agent Bearer credentials cannot mutate canonical endpoints. Health GET /health unauthenticated: {app:'worklog',version,instanceId,dataId,ready:true}. Health outside api prefix.

Final integration additions: bootstrap also returns required dataId, which namespaces all browser drafts/queues/pending idempotency keys. Offline restore rotates dataId and revokes credentials. Legacy/other-context drafts remain untouched and are never imported automatically. /work-items accepts q, roadmapId, bounded limit/offset; list records add isBacklog. POST /work-items/{id}/move {revision:collectionRevision,direction:'up'|'down'} reorders against a server-selected neighbor across pages. Work details include linkedRoadmap {id,title,archived} and linkedStep {id,title,roadmapId,roadmapTitle,retired}. GET /notes/{id}, /tasks/{id}, /references/{id}, /steps/{id} provide bounded review targets. Search results include routeType and routeId. Daily entries retain archived actual work as read-only history. Import commit is idempotent and shares one transaction with search and history. A durable .restore-in-progress.json marker blocks startup after interrupted replacement until an explicit offline restore succeeds.

## Proposals (plans agent)
GET /proposals?status= -> envelope. POST /proposals {title,rationale,operations:[],supersedesId?:uuid} -> draft. {id,title,rationale,status:'draft'|'submitted'|'approved'|'rejected'|'withdrawn',autoApproved,revision,actorId,actorLabel,operations,createdAt,updatedAt,attachments}. PATCH /proposals/{id} {revision,title?,rationale?,operations?} draft only. POST /proposals/{id}/submit|withdraw|approve|reject {revision}. Supported actions: repository.create,repository.update,repository.archive,repository.recover,item.create,item.update,item.archive,item.recover,entry.upsert,note.create,note.update,task.create,task.update,roadmap.create,roadmap.revise,roadmap.move,progress.set,person.create,person.update,person.archive,person.recover,person.link,person.unlink,link.create,link.update,link.archive,link.recover,chat.create,chat.update,chat.archive,chat.recover,github.create,github.update,github.archive,github.recover,question.create,question.update,question.archive,question.recover,decision.create,decision.update,decision.archive,decision.recover. entry.upsert payload includes date,itemId,revision. Never execute code, SQL, arbitrary JSON patch, shell, or remote operations. Proposal evidence uploaded via canonical /attachments with ownerType='proposal', ownerId=proposalId, allowed for owning agent on draft only. Approval updates canonical data/history and proposal atomically through supplied dispatch(conn,actor,action,payload). Evidence promoted to canonical proposal association on approval (readable in review); no direct canonical attachment write by agents.
Approval can be turned off: while `PATCH /settings {requireProposalApproval:false}` is in force, `submit` also approves in the same transaction. It applies every operation as the proposer and records `proposal.submit`, then `proposal.approve` by actor `{id:'automatic-approval',label:'Automatic approval',kind:'human'}`, and returns the proposal `approved`. Any failure (a stale revision, a validation error, a missing target) refuses the submit with that error's status, code and fields, a message starting `Not submitted:`, and nothing applied; the proposal stays a draft. Proposals already submitted when approval is turned off still wait for a human decision. Every proposal record carries `autoApproved`, true only for an automatic approval.

## Repository coordination

These records distinguish canonical repository/work relationships from self-reported agent activity. Repository catalog edits and item/chat `repositoryIds` are canonical: agents submit proposals and a human reviews them. Agent routes permit catalog reads and writes to the caller's own coordination records. The credential authenticates the caller; `externalChatId`, local paths, branches, and run labels are provenance only. Worklog stores repository addresses and reported paths as metadata. The optional address accepts HTTP(S), SSH URLs, and Git SSH addresses such as `git@github.com:org/repo.git`.

All lists below return `{items,total,limit,offset}` with `limit=50` (maximum 200), `offset=0`. Creation and transition POSTs require `Idempotency-Key`; coordination PATCH accepts it too. The CLI requires a caller-supplied `--request-id` for every coordination write. Retry an uncertain result with the same key, route, and payload; select a new key for a new operation. Writes retain bearer redaction, literal-loopback transport, disabled proxies, and redirect refusal.

* `GET /repositories?archived=false&q=` (true lists archived only); `GET /repositories/{id}`: canonical catalog reads. Human `POST /repositories {name,url?,description?}`, `PATCH /repositories/{id} {revision,name?,url?,description?}`, and `POST /repositories/{id}/archive|recover {revision}` manage the catalog. Referenced archived records remain historical context.
* `GET /agent-runs?includeEnded=false`; `GET /agent-runs/{id}`; `POST /agent-runs {clientRunKey,displayName,provider?,externalChatId?}`; `POST /agent-runs/{id}/end {revision}`. A run records a distinct execution context, attributable to its stable communication agent and originating credential. `clientRunKey` is stable within the originating credential. Ending is explicit.
* `GET /participations?repositoryId=&itemId=&runId=&includeReleased=false`; `GET /participations/{id}`. `POST /participations {runId,itemId?:null,description?:'',contexts:[{repositoryId,checkoutPath?,worktreePath?,branch?}]}` reports work across one or more repositories without requiring a work item. A supplied work item must exist. `description` describes current activity (maximum 2,000 characters). `PATCH /participations/{id} {revision,itemId?,description?,contexts?}` replaces supplied fields; `itemId:null` removes the optional work link.
* `POST /participations/{id}/check-in|release|rejoin {revision}` explicitly refreshes reported activity, releases participation, or rejoins. Current revisions protect against lost updates. Multiple participations may overlap: these records are advisory and never block edits or confer operating authority. Two hours without reported activity changes display staleness only; it does not release participation, expire authority, or prove process liveness. No periodic heartbeat or automatic agent wake-up is required.
* `POST /participations/{id}/updates {kind:'update'|'blocker'|'handoff',text}` appends an immutable update. `GET /coordination-updates?participationId=&repositoryId=&itemId=` returns persisted updates scoped to their original context snapshots. Later participation edits do not move past updates to different repositories or work items. `blocker` and `handoff` classify information; they do not enforce a dependency or transfer ownership.
* `GET /context?date=&repositoryId=&itemId=` includes repository/run/participation/update summaries, with optional repository and work filters. Existing daily context remains available when filters are omitted.

The CLI exposes `agent repositories list|show`, `agent runs start|end|show|list`, `agent participation start|update|check-in|release|rejoin|show|list`, and `agent updates post|list`. List reads accept `--limit`/`--offset`; catalog lists accept `--archived`/`--q`, run lists `--include-ended`, participation lists `--repo`/`--item`/`--run`/`--include-released`, and update lists `--repo`/`--item`/`--participation`. `agent context` accepts `--repo` and `--item` alongside `--date`. Catalog mutations are intentionally absent from the agent client allowlist.

For detailed local context, pass a JSON file to `participation start --file` (or `-` for stdin):

```json
{"runId":"RUN_UUID","contexts":[{"repositoryId":"REPOSITORY_UUID","checkoutPath":"C:/Projects/example","worktreePath":"C:/Worktrees/example-task","branch":"codex/task"}]}
```

Use `participation update PARTICIPATION_ID --revision N --file FILE --request-id KEY` with `{itemId,description,contexts}` as needed; omitted fields stay unchanged. To change just the activity description, use `--description TEXT` instead of `--file`. `updates post --participation ID --file FILE --request-id KEY` accepts `{kind,text}`; `--text` defaults to `kind:update` and permits `--kind blocker|handoff`. Posting an update advances the participation revision: read the current participation before its next revision-checked write. Canonical proposals support `repository.create|update|archive|recover` and `repositoryIds` on item/chat create/update operations; approval remains atomic and revision checked. Repository associations use IDs; changing a legacy chat `repos` label does not create or link catalog entries.

## Agent registry

Browser session only: an agent credential gets `403 agent_scope`, because an agent's record joins the tracked chats it reported. The registry writes nothing. Each agent is a stable communication identity (one per credential family, kept across rotation); its record is gathered from the runs, participation, status updates, discussion messages and owned roles it already wrote, so it cannot drift from them. Reported chat IDs, paths and branches remain provenance.

* `GET /agents?limit=50&offset=0` lists `{id,label,active,createdAt,lastActivityAt,providers,openRuns,runCount,messageCount,working,roles}`, agents with an active credential first, then the most recently active. `lastActivityAt` is the latest run start, participation report, status update or message by the agent; a human ending its runs or revoking its credential does not count. `working` holds open participation `{participationId,runId,runName,description,lastSeenAt,stale,item?,roadmap?,contexts}` (an item's roadmap is its step's roadmap, else its own), and `roles` the responsibility roles it owns `{id,label,contextType,contextId,contextTitle,roadmap?,updatedAt}`.
* `GET /agents/{id}` adds `credentials [{id,label,createdAt,revoked,registeredBy}]`, `runs {items,total}` (latest 200, each with the tracked `chats` carrying its `externalChatId`), and the records the agent is tied to: `workItems`, `roadmaps`, `repositories` and `chats`, each `{items,total}` with at most 200 items, current ties first and then the most recent. Every tie carries `via`, the reasons it exists (`participation`, `role`, `update`, `message`, `run`, `chat`), `current` (open participation, an owned role, or a tracked chat reported by an open run) and `lastAt`. Messages tie the agent to their discussion's item, roadmap and step contexts; a tracked chat whose chat ID the agent reported in a run or message ties it to that chat's owner and catalog repositories; work on a roadmap's item also ties the roadmap; a step ties its roadmap.
* `GET /agents/{id}/activity?limit=50&offset=0` pages the agent's discussion messages `{kind:'message',id,createdAt,text,truncated,discussionId,discussionTitle,chatId,chats}` and status updates `{kind:'update',id,createdAt,text,truncated,updateKind,runName,participationId,item?,contexts}` newest first. `text` is the first 1,000 characters; `contexts` is the snapshot kept when the update was posted.
* `GET /roadmaps/{id}/agents` lists who works on a roadmap now, `{items:[{kind:'agent'|'chat',id,label,avatar,provider,model,ties,lastAt,stale}]}`, fresh work first and then the most recent; the Plan & progress outline shows it beside each step. Only current ties count: open participation in the roadmap's work items (an item's roadmap is its step's roadmap, else its own), roles agents own on the roadmap, its steps or its work items, and its tracked chats that are not archived. Each tie is `{stepId,via:'participation'|'role'|'chat',item?,chat?,role?,lastAt,stale}`: participation and a work item's chat or role take the item's step, a roadmap's chat takes each step assigned to it, and work with no step, or on a retired one, has a null `stepId`. A tracked chat is listed under every agent whose run reported its chat ID; one that no run reported is its own `kind:'chat'` entry, with its title as `label` and its provider and model. `stale` marks participation not reported for two hours, and a worker is `stale` when all its ties are. Agents have their `avatar`; a chat has none.

## Agent self-registration

An agent credential registers a separate identity for the agent holding it; see the README for the CLI. The registering credential is the only authority, and the new identity gets the same agent scope, nothing more. Neither route writes an idempotency receipt, since a receipt's request hash would derive from the token.

* `POST /agent-registrations {label,token,avatar?}` with an agent bearer creates a credential whose token is the caller-generated `token` and binds it to a new identity. The token is 43–200 characters of `A-Z`, `a-z`, `0-9`, `-`, `_`; generate it from at least 32 random bytes, for example with `secrets.token_urlsafe(32)`. A token with fewer than 10 distinct characters is refused as `422`. The label `You`, which names the person, is refused too. It returns `{id,agentId,label,avatar,registeredBy:{id,label}}`, never the token; `registeredBy` is the registering agent's identity. Only the token's SHA-256 is stored. The token is the idempotency key: repeating the request with an active registered token returns that registration unchanged, a revoked one is `409 token_revoked`, and the token of a credential issued in Settings is `409 token_in_use`. A person's session gets `403 agent_scope` and a taken avatar `409 avatar_in_use`. When 200 registered identities are active, or agents registered 200 since local midnight, the request gets `429 agent_limit`. Credentials issued in Settings never count.
* `POST /agent-registrations/retire {}` with a registered credential's bearer revokes that credential, ends its open runs and releases their participation with reason `credential_retired`. It also revokes every identity it registered, as below. It returns `{id,agentId,retired:true,registeredRevoked}`. A credential issued in Settings, or a person's session, gets `403 agent_scope`; the retired token then gets `401`.
* `POST /credentials/{id}/revoke` also revokes every active credential of the identities registered by that credential's identity, directly or through the ones they registered. It ends their open runs (`credential_revoked`) and returns `{ok:true,registeredRevoked}`. Rotation keeps them, because it keeps the identity.
* The `credential.register`, `credential.retire` and `credential.revoke` events record each change; a revoke that followed from another carries `via`, the credential revoked first. Settings `credentials` and `GET /agents/{id}` `credentials` carry `registeredBy {id,label}`, or `null` for a credential issued in Settings. Settings `credentials` also carry `registeredActive`, the number of active identities that revoking the credential would revoke.

## Messages to a chat's agents

The person writes into a tracked chat; agents receive. Recipients are fixed when a message is sent: every open run whose `externalChatId` equals the chat's `chatId` exactly, on a credential that is not revoked (the registry's current run tie). Writes require `Idempotency-Key`.

* Browser session only (an agent credential gets `403 agent_scope`, as it does for `GET /history` of a message): `GET /chats/{id}/messages?limit=50&offset=0` returns `{chat:{id,chatId,archived},recipients,items,total,limit,offset}`. `recipients` lists `{runId,runName,provider,startedAt,agentId,agentLabel,avatar}` a message sent now would reach, and is empty for an archived chat. `items` are newest first: `{id,chatId,text,authorId,authorLabel,createdAt,deliveries}`, each delivery `{runId,runName,agentId,agentLabel,avatar,status:'pending'|'delivered'|'expired',reason,expiresAt,deliveredAt,expiredAt}`.
* `POST /chats/{id}/messages {text}` (Markdown, at most 1,000,000 UTF-8 bytes) returns the message with its deliveries. `409 chat_archived` refuses an archived chat, which stays archived; `409 no_recipients` refuses a chat with no open, tied run. Neither stores anything.
* Agent only: `POST /inbox/receive {chatId?}` hands the caller's credential its waiting messages, oldest first, and marks them delivered, so each arrives once; two open runs on one chat still get one copy, `{id,text,authorKind:'human',authorId,authorLabel,sentAt,chat:{id,chatId,title},runIds}`. `chatId` limits it to runs that reported that chat ID. A run must still be open and tied to the chat when a message is handed out. Retrying an uncertain result with the same key returns the same messages, and nothing that request did not already receive; an empty result keeps no receipt. The CLI is `agent inbox [--chat CHAT_ID] [--request-id KEY]`.

A pending delivery expires, with `reason`, when its run ends (`run_ended`, or `human_closed` when you end it), its credential is revoked or rotated (`credential_revoked`, `credential_rotated`), its agent retires (`credential_retired`), its chat is archived (`chat_archived`) or its `chatId` is changed (`chat_changed`), or a restore ends every run (`restore`). Recovering the chat afterwards does not revive it. A delivery still pending at `expiresAt`, two hours after sending, reads as expired with reason `not_picked_up` and is never handed out. No route recovers a chat, reopens a run, or touches a provider session.

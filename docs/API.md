# Worklog implementation contract

The discussion API extends the original contract below. See the [agent guide](AGENT-GUIDE.md) (section 5.7) for operating semantics and CLI examples. Generated request contracts are in `openapi.json`.

## Discussions

All discussion writes require `Idempotency-Key`. Authentication selects the actual author; clients cannot supply one. Discussion retry receipts use stable communication identity while existing proposal identity is unchanged.

- `GET /discussions/participants` returns identities, each with its generated `avatar` name (`null` for the person), and the caller. `GET /discussions/avatars` lists every avatar `{name,available}`, a fresh `suggested` draw and the caller's `current` one; `available` is false when another agent with a live credential shows it. An agent's `POST /discussions/avatar {avatar}` changes its own avatar and returns its participant record; an avatar another active agent shows is `409 avatar_in_use`, and the person gets `403`. `GET /discussions` supports `view=all|awaiting|archived`, `q`, `contextType` and `contextId`, `pinned=true|false`, the legacy `repo` label filter, `limit` and `offset`, and lists pinned conversations first (the latest pinned first), then the rest by `updatedAt`. `POST /discussions` creates a conversation and first message, tagged with up to 30 `contexts` `{type,id}`; a non-empty `repos` returns `422 validation` with `fields.repos` `retired` (K8).
- `GET /discussions/{id}` pages immutable messages. `POST /discussions/{id}/messages` replies. Bodies support optional `chatId`, `onBehalfOfRoleId`, and `acknowledgement` with `mode=all|any|any_agent|anyone` and named `targets` where applicable.
- `GET /discussions/messages/{id}` returns a message and its request state, target slots, receipts, allowed target IDs and cancellation/release capabilities. `POST .../acknowledge` accepts explicit `targetIds` (optional only for open audiences); `.../cancel` checks current management authority. Human-only `.../release` requires `reason`.
- Human-only `POST /discussions/{id}/archive` takes `revision` and `archived`. Archived conversations remain replyable; pending requests remain discoverable.
- Tags (schema v22): `POST /discussions/{id}/tags {type,id}` tags a conversation with a record, and `POST /discussions/{id}/tags/remove {type,id}` takes the tag off; both return the summary, and a tag already there, or not there, changes nothing. A ticket may be named by its key or number. The record must exist (`422 validation`, an unknown ticket key included; a filter by one finds nothing); a merged repository returns `409 repository_merged` with `fields.repositoryId`. A conversation holds 30 tags. Agents remove only the tags they added (`403 forbidden`, `fields.contextId` `not_yours`); nobody removes a repository's tag from its own discussion (`fields.contextId` `home`). Each summary `context` carries its record's `title`, `archived` and summary fields (as an agent tie's `target`), `home`, `addedBy {id,label,kind}` and `addedAt`; a context a role contributes has `addedBy` null. Tags and pins advance `revision` without touching `updatedAt`.
- Human-only `POST /discussions/{id}/pin {revision,pinned}` pins or unpins; summaries carry `pinned` and `pinnedAt`. A repository's own discussion, which Worklog opens as the person whenever a repository is registered, carries `repository {id,name}`; a rename retitles it (`discussion.retitle`), and a merge retags the merged repository's conversations with the survivor.
- `GET /discussions/roles` pages context roles. `POST /discussions/roles` creates `{contextType,contextId,label}`. `POST /discussions/roles/{id}/{claim|release|accept|decline|withdraw}` takes `revision`; `offer` adds `successorId` and optional `note`. Human-only `reassign` adds `ownerId` (nullable) and required `reason`.
- `GET /discussions/resume` returns a consistent context snapshot and cursor; `GET /discussions/changes` incrementally reads ordered changes, `discussion.tag`, `discussion.untag`, `discussion.pin`, `discussion.unpin` and `discussion.retitle` among them; an untag also reaches the feed of the record it named. Cursors bind dataset, context scope and sequence; invalidated cursors return `409 cursor_reset`. Resume/changes have bounded pagination.
- `POST /credentials/{id}/rotate` accepts an optional `label`, revokes replaced credentials and returns a one-time token bound to the same communication identity. Replaying the same mutation redacts that token. Settings includes retained identities and each credential's `agentId`.

Context (tag) types are `item`, `roadmap`, `step`, `repository`, `ticket`, `release`, `person`, `resource`, `question` and `decision`; roles take only `item`, `roadmap` and `step`. Acknowledgement target kinds are `agent`, `human`, and `role`; the human ID is `local-user`. Requests are `pending`, `satisfied`, `released_by_human`, or `cancelled`. Role ownership changes atomically with assignment generation. Receipts retain actual actor and generation; reading/replying/handoff is never receipt.

## Original workbench contract

Owner: root; task WORKLOG-BUILD. Local-only, new repository. Root owns database primitives, work/day/context services and API integration. Plans agent owns plans.py, proposals.py and corresponding tests. Frontend agent owns frontend/. Operations agent owns cli.py, recovery.py, scripts/, README.md and corresponding tests. Shared files require parent coordination. No commits by children.

All API routes start /api/v1. camelCase JSON. UUID ids, integer revision; timestamps UTC ISO strings. Date strings YYYY-MM-DD in configured America/Chicago timezone. Work item states are open, doing, waiting, blocked, done; ticket and roadmap step states are open, doing, blocked, done. Every mutation sends a JSON object (raw uploads excepted), includes revision for existing records, and an Idempotency-Key header for creates/approval. A retry with the same key and payload replays the first response while its receipt is kept: 14 days. Error: {error:{code,message,fields?}}. A JSON body whose text holds a lone UTF-16 surrogate (a valid escape such as `\ud800` that names no character, or its raw bytes) is refused before any route reads it, with 422 validation and fields {path:'invalid'}, where path is the field's dotted place such as `operations.0.payload.title`; a surrogate pair, as json.dumps escapes an emoji, is ordinary text. Conflict 409. Envelope lists {items:[...],total:n}; objects returned directly. Session bootstrap POST /session/bootstrap body {} and X-Worklog-Bootstrap: 1 returns {csrfToken,today,timezone}; fetch credentials same-origin, X-CSRF-Token on cookie writes. Agent Bearer credentials cannot mutate canonical endpoints. Health GET /health unauthenticated: {app:'worklog',version,instanceId,dataId,ready:true}. Health outside api prefix.

Final integration additions: bootstrap also returns required dataId, which namespaces all browser drafts/queues/pending idempotency keys. Sessions live in server memory, so a restart drops them; bootstrap returns the current session's token while that session is valid. The browser client renews on 401 session, or on 403 csrf after another tab renewed: it checks that GET /health still reports its dataId, bootstraps, and resends once with the same Idempotency-Key; another dataId stops it with 409 data_context until the page reloads. Offline restore rotates dataId and revokes credentials. Legacy/other-context drafts remain untouched and are never imported automatically. /work-items accepts q, roadmapId, bounded limit/offset; list records add isBacklog. POST /work-items/{id}/move {revision:collectionRevision,direction:'up'|'down'} reorders against a server-selected neighbor across pages, within the unscheduled backlog. Work details include linkedRoadmap {id,title,archived} and linkedStep {id,title,roadmapId,roadmapTitle,retired}. GET /notes/{id}, /tasks/{id}, /references/{id}, /steps/{id} provide bounded review targets. Search results include routeType and routeId. Daily entries retain archived actual work as read-only history. Import commit is idempotent and shares one transaction with search and history. A durable .restore-in-progress.json marker blocks startup after interrupted replacement until an explicit offline restore succeeds.

## Work and days
GET /work-items?view=all|backlog&status=&roadmapId=&personId=&archived=false&limit=100&offset=0; repeat status (`status=open&status=doing`) to match any of several states, and leave it out or empty for every state. POST /work-items {title,description:'',adoUrl:null,roadmapId:null,stepId:null,day?:date,worked?:bool}. Item {id,title,description,status,adoUrl,roadmapId,stepId,people:[...],backlogOrder,archived,revision,createdAt,updatedAt}. PATCH /work-items/{id} {revision,...fields}. POST /work-items/{id}/archive or /recover {revision}. POST /work-items/reorder {ids:[all active backlog ids],revision:collectionRevision}; the backlog trades the positions it holds, so planned work keeps its stack rank. List includes collectionRevision.
Stack rank: unfinished, unarchived items are ranked 1..n in backlogOrder order, the one order every item keeps. List records, work details and day entries' items carry rank (null for done or archived work); lists and details add rankedCount, the number of ranked items whatever the filters. Lists show ranked work first, by rank, then the rest by backlogOrder. POST /work-items/{id}/rank {revision:itemRevision,rank:n>=1} moves the item there, last when n passes the last rank, and returns {id,rank,rankedCount}; it records item.rank history {rank} before and after, and changes no item's revision, so open drafts still save. A done item is 409 conflict and an archived one 404. Done and archived items keep their place in the order and rejoin the ranking there when reopened or recovered; new items start last.
GET /days/{date} -> {date,revision,reflection,reflectionRevision,entries:[{id,itemId,date,planned,worked,outcome,position,revision,item:WorkItem,counts:{tasks,tasksDone,links,files,scratchpad},statusOnDay}],summary:{worked:[...],completed:[...],blocked:[...]},nextItemId}. An entry's statusOnDay is the status its item ended {date} with, folded from the item's history like summary.blocked, so later changes leave an earlier day's value alone; an item with no history by then (work logged after its day) has its status now. PUT /days/{date}/entries/{itemId} {revision:0 for create or existing revision,planned?,worked?,outcome?}. PUT /days/{date}/reflection {revision:reflectionRevision,text} -> {date,reflection,revision} with the reflection's new revision. POST /days/{date}/reorder {revision:dayRevision,ids:[entry ids]}. The day's revision guards which entries it holds and their order (K4): adding or removing an entry, or a reorder, raises it, while a change to an entry's planned, worked or outcome raises only the entry's revision. The reflection has its own revision (schema v21), which only a reflection save raises, so new work and reorders leave a reflection draft able to save; a day with no row yet has both revisions at 0. A reorder leaves each entry its revision, as a backlog reorder or move leaves each work item its own. POST /days/{date}/reschedule {itemId,targetDate,revision:entryRevision,targetRevision:0|existing} plans the item on targetDate. Its entry on {date} stays, no longer planned, when it records work (worked, or an outcome other than blank space); an entry that only planned the item is removed as /remove removes it, with `entry.remove` history. The item needs an entry on {date}: none is 409 `conflict`. POST /days/{date}/entries/{itemId}/remove {revision:entryRevision} takes the item off the day and returns {ok:true}: the entry goes with its planned, worked and outcome, so neither the day nor the item's dailyEntries list it, and history records `entry.remove` with the entry as before and null as after. The item itself is unchanged, and rejoins the backlog when no other day from today on plans it. A stale revision or an entry already gone is 409 `conflict`; an archived or unknown item is 404, since an archived item's entries are read-only history. Only the person's session may call it; agents are refused.
GET /work-items/{id} -> item plus {rank,rankedCount,dailyEntries,notes,tasks,attachments,references,history}. A day entry's counts say what its item's tabs on Today hold before the item is read: active tasks and how many are done, active links, active attached copies and local paths together, and whether the scratchpad has text other than whitespace. GET /history?entityId=&limit=100 returns list envelope.

## People and links
GET /people?archived=false&q= -> list envelope of {id,name,title,team,description,email,phone,chat,location,notes,archived,revision,createdAt,updatedAt,workItemCount,roadmapCount,repositoryCount}; the counts leave out archived targets, and `q` searches every field. POST /people {name,title:'',team:'',description:'',email:'',phone:'',chat:'',location:'',notes:''}. GET /people/{id} -> person plus {roadmaps:[{linkId,personId,roadmapId,relationship,createdAt,roadmap}],workItems:[{linkId,personId,itemId,relationship,createdAt,item}],repositories:[{linkId,personId,repositoryId,relationship,createdAt,repository}],history}. PATCH /people/{id} {revision,name?,title?,team?,description?,email?,phone?,chat?,location?,notes?} changes only the fields it names. POST /people/{id}/archive or /recover {revision}.
Field rules: `team` is what v9 called `role`, which is now refused (422). `name` (required), `title`, `team`, `chat` and `location` are trimmed single lines of at most 500 UTF-8 bytes; a line break or other control character in one is refused as it is set, so a value kept from v9 blocks no other change. `email` is empty or one address with a dotted domain and no whitespace, control characters or `<>()[]\,;:"?#/%` (320 bytes); `phone` is empty or printable text with at least one digit, in any script (100 bytes); `description` is up to 10,000 bytes and `notes` Markdown up to 1,000,000. A field that breaks a rule returns 422 `validation` with `fields:{<field>:'invalid'}`. A proposal operation with fields its action does not take is refused with a message that names them, and `fields:{missing,unknown}`.
POST /person-links {personId,targetType:'item'|'roadmap'|'repository',targetId,relationship:''} creates or updates a person link (the person's role there) on a work item, roadmap or repository, and returns {id,personId,name,personTitle,personTeam,targetType,targetId,relationship,archived,createdAt}. The person must be active. A new link to a repository needs an active one: 409 `archived` or `repository_merged`, with `fields.repositoryId`; an existing link's relationship can still change. An unknown target returns 404. POST /person-links/unlink {personId,targetType,targetId} removes the link. Work item, roadmap and repository details carry `people:[{id,personId,name,personTitle,personTeam,relationship,archived,createdAt}]`, by name; `personTitle` and `personTeam` replace v9's `personRole`.

## Agent ties (schema v17)
An agent identity is tied to a record with a relationship (its role there). The person ties any agent; an agent ties only itself, directly, and changes or removes only ties it set. A tie records `setBy`: `'human'` when the person set it or last changed it, `'agent'` when the agent did. Ties are informational: they reserve and lock nothing, grant no authority, and never deliver a chat's messages.
* Types: `item`, `roadmap`, `step`, `repository`, `person`, `resource`, `discussion`, `proposal`, `ticket`, `agent`, `question`, `decision`. A tracked chat is not a type: its agents are the identities bound to it, by registration or by the person's confirmation (see Messages to a chat's agents), and a confirmation also delivers the chat's messages.
* `POST /agent-links {agentId?,targetType,targetId,relationship:''}` creates or changes a tie and returns it. The person must give `agentId`; an agent may leave it out, and naming another agent is `403 forbidden`. An agent changing a tie the person set gets `403 forbidden`; the person changing an agent's tie makes it theirs. `relationship` is at most 200 bytes, trimmed. A ticket's `targetId` may be its key or number (`T-12`, `12`); the tie stores its ID. A new tie needs a repository that is active and not merged (409 `archived` or `repository_merged`) and a step that is not retired (409 `conflict`); an agent cannot be tied to itself (422 `validation`). An unknown agent or record, or another agent's draft proposal, is 404 `not_found`. An agent holds at most 500 ties it set itself (429 `agent_limit`). Setting the same role again from the same side writes nothing; the person setting an agent's tie, even with the same role, makes it theirs. Idempotency-Key required; agent writes are made by the agent's identity, so a retry survives a token rotation, and a credential revoked while the call waited is refused (401).
* `POST /agent-links/unlink {agentId?,targetType,targetId}` removes a tie and returns `{ok,id,agentId,targetType,targetId}`; the same rules decide who may. 404 when there is no such tie. Idempotency-Key required.
* `GET /agent-links?agentId=` lists one agent's ties; `GET /agent-links?targetType=&targetId=` (repeat `targetId`, at most 200) lists the ties on those records; an agent calling with neither gets its own. Each returns `{items,total}`: at most 500 ties, in the order the types are listed, agents with a live credential before the others, then by name. A tie is `{id,agentId,agent:{id,label,avatar,active},targetType,targetId,target,relationship,setBy,createdAt}`. `target` is `{id,title,archived}` (archived: a retired step, an archived or merged repository, an agent with no live credential) with, by type, `status` (item, step, proposal, ticket, question), `roadmapId` and `roadmapTitle` (step, question, decision), `number` (ticket), `mergedInto` (repository) and `avatar` (agent); it is null for a record that no longer resolves. An agent never reads a tie to another agent's draft proposal, nor its entries in history (`GET /history`).
* Each tie is recorded as `agent.link` or `agent.unlink` in the history of both the agent and the record, with `{agentLabel,targetTitle,relationship,setBy}` as they stood. A repository merge moves its ties to the survivor, which keeps its own when an agent was tied to both, unless only the merged repository's tie was the person's, which then takes its place; the merge event's `moved.agents` counts them. Export includes `records/agent_links.json`.
* `GET /context` carries `ties`: the calling agent's ties as above, and `{items:[],total:0}` for the person.

## Supporting records
Notes {id,ownerType:'item'|'roadmap'|'step',ownerId,title,text,revision,archived,...timestamps}; POST /notes, PATCH /notes/{id}, POST /notes/{id}/archive|recover. Markdown text, title optional. A work item has one scratchpad, its only active note: creating or recovering a second one there is 409 `conflict`, and a scratchpad may be saved empty. Schema v8 folded each item's active notes into its oldest one, each titled note as a `## title` section, and archived the rest. An approved proposal's `note.create` for a work item lands in its scratchpad: appended as a section, or starting it. Tasks similar, {text,done,itemId,...timestamps}; POST /tasks, PATCH /tasks/{id}, archive/recover. A task's `createdAt` is when it was added and `updatedAt` when its text or done state last changed; a new task has the two equal. A work item's `tasks` come in the person's order (schema v14), archived ones included, and a new task goes last. POST /tasks/{id}/move {revision:taskRevision,position} moves an active task to that 1-based place among its work item's active tasks, a place past the last moving it last, and returns {id,position}. It is checked against the task's own revision and changes no task's revision or `updatedAt`, so an edit open on any task still saves; an archived task is 409 `conflict`, and keeps its place among the rest until it is recovered. Moves record `task.move` with the place before and after; agents get 403 `agent_scope`. References {itemId,path}; POST /references, archive/recover.
Links {id,ownerType:'item'|'roadmap',ownerId,url,title,description,revision,archived,...timestamps}; POST /links, PATCH /links/{id}, archive/recover.
Agent chats {id,ownerType:'item'|'roadmap',ownerId,chatId,title,createdDate,provider,model,repos:[string],stepIds:[stepId],revision,archived,...timestamps}; POST /chats, PATCH /chats/{id}, archive/recover. provider and model are free text; repos holds at most 20 distinct names. stepIds is the complete list of steps a roadmap chat works on (always empty for a work item's chat): every step must belong to the chat's roadmap, a retired step can stay but not be newly assigned, and each assignment change records chat.assign or chat.unassign in that step's history. Agents claim steps by proposing chat.create or chat.update with stepIds, or, for the chat they registered with, directly with `POST /chats/track` (see Repository coordination).
Chat history (browser session only; an agent credential gets 403 agent_scope) reads the transcripts Claude Code and Codex keep on this machine, never writing them. GET /chats?archived=false lists every agent chat with owner {type,id,title,archived}, roadmaps [{id,title,archived}] (the roadmaps the owner sits within, top level first: a roadmap's own chat ends with that roadmap, a work item's chat with its step's roadmap or else its roadmapId, and a work item on no roadmap has none), steps [{id,title,status,retired}], agents [{id,label,avatar,active,binding:'registered'|'confirmed'|'run',chatId}] (the identities registered with the chat's ID, confirmed in it, or, only a claim, with an open run on a live credential that reports it, each once with its closest tie; IDs are compared exactly, as delivery compares them, and `chatId` is the tie's ID as stored) and transcript {found,source:'claude'|'codex'|null,lastActivityAt,state:'working'|'idle',threads:[{key,name,title,task,parent,model,state,lastActivityAt}],error?} (error set when a transcript exists but cannot be read, without failing the list). GET /chats/{id}/transcript?limit=200&thread=key (limit 1-2000) returns {chat,...transcript,messages,total,more}: the latest limit messages oldest first (thread narrows them to that agent's transcript and what it sent), each {id,thread,at,kind:'user'|'assistant'|'agent'|'tools',author,authorThread?,recipient?,text?,truncated?}, a tools run adding {count,until,tools:[{name,summary}]} for consecutive tool calls. A chatId finds a transcript only in the shape those tools use: a Claude Code session UUID under ~/.claude/projects (CLAUDE_CONFIG_DIR), a Claude desktop local_ session ID resolved to the Claude Code session it runs, or a Codex thread ID under ~/.codex/sessions or archived_sessions (CODEX_HOME). A Claude session includes its subagents; a Codex thread that started agents includes every thread sharing its session. agent messages are the ones agents send each other (SendMessage, subagent prompts, Codex agent messages), named by tracked chat title or desktop session title where known. Tool context, system reminders and tool output are left out, text over 20,000 characters is shortened, each transcript keeps its latest 2,000 messages (older ones still count in total, but more is true only while a larger limit would show earlier kept messages), and a line over 32 MB or not JSON is skipped. A thread is working while its latest turn is open and its file changed in the last 15 minutes.
Running sessions (browser session only; an agent credential gets 403 agent_scope). `GET /claude-sessions` lists the Claude Code sessions running on this machine, `{items:[{sessionId,hostSessionId,chatId,name,cwd,entrypoint,kind,status:'working'|'waiting'|'idle',waitingFor,startedAt,statusAt,version,model,tracked,agents}]}`, those waiting on the person first, then working, then idle, each the most recently changed first. Claude Code keeps a record of each running session, `sessions/<pid>.json` in its configuration folder (CLAUDE_CONFIG_DIR, else ~/.claude). A record counts only while a process with its `pid` runs and, on Windows, started at its `procStart` (with none recorded, no later than its `startedAt`), so a record an ended process left behind, or one whose process ID was reused, is passed over. The newest 1,000 records are read. One over 64 KB, or whose name, `pid` (1 to 2,147,483,647) or `sessionId` does not fit, is skipped, and on Windows so is one whose `pidDomain` names another system's processes, such as WSL's. A session recorded twice counts once. `sessionId` is Claude Code's session ID and `hostSessionId` the Claude desktop session running it (`local_...`) or null. `status` is Claude Code's busy, waiting or idle (any other reads as idle), and `waitingFor` says what a waiting session waits for. `name` is the session's name, else its transcript's title, its desktop session's title or its folder's name; `model` comes from its transcript. `tracked` lists the agent chats that track either ID, compared without case, `{id,title,archived,ownerType,ownerId,ownerTitle}`, active ones first; Chats offers a session while none of them is active. `agents` lists the identities tied to either ID, as in `GET /chats` but compared without case, each `chatId` the ID its tie was stored under; delivery reaches only those whose `chatId` is the one the session is tracked by. `chatId` is the ID to track it by: the one its closest-tied agent uses (registered, then confirmed, then an open run's), else one a record tracks it under, else `sessionId`. Worklog only reads these records, and opens a process only to ask whether it runs and when it started.
GitHub references {id,ownerType:'item'|'roadmap',ownerId,kind:'commit'|'pr',url,reference,title,description,chatId,chatTitle,revision,archived,...timestamps}; POST /github, PATCH /github/{id}, archive/recover.
Roadmap questions {id,roadmapId,title,details,answer,status:'open'|'answered',revision,archived,...timestamps}; POST /questions {roadmapId,title,details:''} always opens a question; PATCH /questions/{id} {revision,title?,details?,answer?,status?}; archive/recover. Marking a question answered needs a nonblank answer (422 fields {answer:'required'}); reopening keeps the answer. Roadmap decisions {id,roadmapId,title,rationale,decidedDate,revision,archived,...timestamps}; POST /decisions {roadmapId,title,rationale:'',decidedDate?:date} (today in the configured timezone when omitted or blank); PATCH /decisions/{id} {revision,title?,rationale?,decidedDate?} keeps the date when decidedDate is omitted and rejects a blank one (422 fields {decidedDate:'required'}); archive/recover. details, answer and rationale are Markdown up to 100,000 UTF-8 bytes; titles up to 1,000. Roadmap details list questions oldest first and decisions newest decidedDate first; search indexes both and routes to the roadmap. Agents add them by proposing question.* or decision.* operations with the same fields.
GET /attachments?ownerType=&ownerId=&archived=false metadata envelope, oldest first; POST /attachments?ownerType=&ownerId=&name= raw bytes Content-Type, 25,000,000 byte max. GET /attachments/{id}?download=1 authenticated bytes. POST archive/recover {revision}. {id,name,mime,size,sha256,revision,archived,ownerType,ownerId,createdAt}. ownerType is item, roadmap, step, repository or proposal (agent evidence, see Proposals); a repository holds files only, no notes. Agents upload only evidence; a file reaches the person's records from an agent only as an approved `attachment.create`, a copy of that evidence. Only an active repository takes uploads: an archived one returns 409 `archived` and a merged one 409 `repository_merged`, both with `fields.repositoryId`. An archived repository's files can still be read, archived and recovered; a merged one's have moved to the survivor. Search indexes a file by name and routes a repository's files to `routeType:'repositories'` and the repository's ID, filed with the archive while the repository is archived. Notes max1,000,000 UTF8 bytes. Paths copy only.

## Roadmaps (plans agent owns exact implementation matching this contract)
GET /roadmaps?archived=false&personId=&q= -> list envelope of {id,title,overview,parentId,revision,archived,people,...}; `personId` keeps the roadmaps tied to that person, and `q` those whose title holds every word of it, in any case. POST /roadmaps {title,overview:'',steps:[],parentId?:activeRoadmapId}. Roadmaps nest: parentId names the parent roadmap (null at the top level). POST /roadmaps/{id}/move {revision,parentId:id|null} changes only the placement, records roadmap.move history and no version; the parent must be active and neither the roadmap nor one of its sub-roadmaps. Revisions and restores keep the placement, and archiving keeps children's parentId. GET /roadmaps/{id} -> {id,title,overview,parentId,ancestors:[{id,title,archived}] top level first,children:[{id,title,archived}],revision,archived,steps:[{id,title,description,parentId:null,position,status,revision,retired}],versions:[{number,createdAt,note}],workItems:[...],notes,attachments,history}. Steps form a tree with stable UUIDs. POST /roadmaps/{id}/revisions {revision,title,overview,steps:[{id?:uuid,title,description,parentId:null,position,retired?:bool}],note:''}. A step marked `retired: true`, as GET lists a retired one, stays out of the plan as one left out does: it is retired, or stays retired. A revision or restore writes only what it changes (K4): a step that keeps its title, description, parent and place among its siblings, and stays active, keeps its revision and gets no event, though its position number may change; numbering the positions afresh, or adding or retiring a step before it, moves no other step, and of siblings put in a new order the fewest that account for it count as moved (of two neighbours swapped, the one now first). A save that changes nothing records no revision, version or event. Its `roadmap.revise`, `roadmap.restore` or `roadmap.create` event records `{versionNumber,changedStepIds}`; the version holds the whole plan, and each changed step's own event its before and after. GET /roadmaps/{id}/revisions/{number} -> immutable {number,createdAt,note,title,overview,steps}. POST /roadmaps/{id}/restore {revision,number}. POST archive/recover {revision}. PATCH /steps/{id}/progress {revision,status} raises the step's revision only: the roadmap's revision guards its title, overview and step tree, which progress leaves alone. PATCH /steps/{id} {revision:stepRevision,title?,description?} changes one step's text without the rest of the plan (K15): each field given replaces the step's, a title trimmed and required. It writes that step alone and records `step.update` history and no version. It raises the step's revision and the roadmap's, so a revision drafted before it is refused (409 `conflict`) rather than writing the old text back, while changes to other steps stay current. Text the step already has records nothing. A retired step or an archived roadmap is 409 `conflict`, and neither field 422 `validation`. Agents propose it as `step.update`. GET /steps/{id}/history. Retired steps retain progress and identity, parent progress derived.
POST /imports/preview?name= raw HTML <=5,000,000 bytes -> {id,title,overview,steps:[...candidate UUIDs...],warnings,sha256}. POST /imports/{id}/commit {title,overview,steps,roadmapId?:existing,revision?:existingRoadmapRevision}; new roadmap from selection or attach original as reference (no merge). Original bytes downloadable via GET /imports/{id}/download with forced attachment. Candidate overview/body Markdown; no original HTML inline.
GET /steps/{id} -> the step {id,title,description,parentId,position,status,revision,retired} with its roadmapId, notes and attachments. The agent CLI reads it as `agent step show ID`, and `GET /roadmaps/{id}` as `agent roadmap show ID`, which leaves out `history` because each roadmap event holds whole before-and-after copies of the plan. These two reads are the only `/roadmaps` and `/steps` routes in the CLI's allowlist; agents change roadmaps and progress through proposals.

## Proposals (plans agent)
GET /proposals?status=&limit=50&offset=0 -> envelope: the proposals the caller may see, oldest first, a page of `limit` (1 to 200) from `offset`; `total` counts every one the caller may see with that status. `GET /context` still lists them all. Agent quotas (K10), counted from the proposals and attachments tables for an agent identity under any of its credentials: it keeps at most 50 drafts, so creating, superseding or its own `reopen` past that gets 429 `agent_limit`; while approval is on, at most 100 of its proposals await review, so a 101st `submit` gets the same. A proposal holds at most 20 evidence files and 100,000,000 bytes of them, archived ones included, and an agent's upload past either gets 429 `agent_limit`. The person has no such limit. POST /proposals {title,rationale,operations:[],supersedesId?:uuid} -> draft. {id,title,rationale,status:'draft'|'submitted'|'approved'|'rejected'|'withdrawn',autoApproved,revision,actorId,actorLabel,actorDirectory,operations,createdAt,updatedAt,submittedAt,attachments}; `submittedAt` is the time of its latest `proposal.submit` event while submitted (null while a draft), and `updatedAt` moves with every edit and transition. `actorDirectory` (schema v18) is the `directory` the proposer's identity registered with, whichever of its credentials wrote the proposal; it is null for the person, a credential issued in Settings, or an identity that registered without one. PATCH /proposals/{id} {revision,title?,rationale?,operations?} draft only. POST /proposals/{id}/submit|reopen|withdraw|approve|reject {revision}. `reopen` returns a `submitted` proposal to `draft` (allowed for the owning agent or the person) so the agent can update its operations in place while keeping uploaded evidence; when the person reopens a proposal, or when a plan change (`roadmap.*`, `progress.set` or `step.update`) makes a `submitted` proposal's target revision stale, Worklog notifies the proposing agent via a roadmap-scoped discussion acknowledgement request and any open run tied to a tracked chat. Operations {action:string,payload:object}; existing targets must carry revision in payload. Supported actions: repository.create,repository.update,repository.archive,repository.recover,item.create,item.update,item.archive,item.recover,entry.upsert,note.create,note.update,task.create,task.update,roadmap.create,roadmap.revise,roadmap.move,progress.set,step.update,person.create,person.update,person.archive,person.recover,person.link,person.unlink,link.create,link.update,link.archive,link.recover,attachment.create,chat.create,chat.update,chat.archive,chat.recover,github.create,github.update,github.archive,github.recover,question.create,question.update,question.archive,question.recover,decision.create,decision.update,decision.archive,decision.recover,resource.create,resource.update,resource.archive,resource.recover,ticket.create,ticket.update. entry.upsert payload includes date,itemId,revision. `ticket.update`'s `id` is the ticket's UUID, key or number. Names: on any create but `attachment.create`, and `note.create` on a work item (it joins the item's scratchpad; `not_nameable`), `id` is a name for the new record, never an ID: `@` and 1 to 100 letters, digits, `.`, `_` or `-`, the first a letter or digit. A later operation gives the name in `id`, `itemId`, `roadmapId`, `parentId`, `personId`, `ownerId`, `targetId` or an entry of `repositoryIds`, for a record of the kind that field takes (for `ownerId` and `targetId`, the kind `ownerType` or `targetType` names; a step can't be named). Create and update refuse, and submit and approve check again, a name no earlier operation declares, one declared twice, one of the wrong kind, or a malformed one: 422 `validation` with `Change N of M, ACTION:`, and `fields.fields` `{FIELD:'unknown_name'|'duplicate_name'|'wrong_kind'|'invalid_name'|'not_a_name'|'not_nameable'}`. Approval replaces each name with the ID of the record it stands for, including the record a `repository.create` for an already-registered remote links to; the stored proposal keeps its names. Resource and ticket operations run as the proposer, the same as the others; a ticket's author is the proposing credential's stable identity, even if that credential was rotated or revoked before approval. Never execute code, SQL, arbitrary JSON patch, shell, or remote operations. Proposal evidence uploaded via canonical /attachments with ownerType='proposal', ownerId=proposalId, allowed for owning agent on draft only. Approval updates canonical data/history and proposal atomically through supplied dispatch(conn,actor,action,payload). A failed operation keeps its status and code, its message starts `Change N of M, ACTION:` with N its 1-based position in `operations`, and `fields` becomes `{operation:N,action,fields}` holding the operation's own fields. Evidence promoted to canonical proposal association on approval (readable in review); no direct canonical attachment write by agents. `attachment.create {ownerType:'item'|'roadmap'|'step'|'repository',ownerId,attachmentId}` attaches a copy of a file uploaded to the same proposal: applying it inserts a new attachment on the owner with the evidence's name, MIME type and bytes, indexes it for search, and records `attachment.create` by the proposer; the evidence stays with the proposal. Worklog adds the proposal's ID when it applies the operation, and a payload naming `proposalId` is refused like any unknown field. `attachmentId` must name a file of that proposal: anything else (another draft's evidence, a canonical file, an unknown ID, the evidence of a proposal this one supersedes) gets the same 422 `validation` with fields `{attachmentId:'not_evidence'}`, and a file archived from the proposal 409 `archived`. Create and update refuse a second `attachment.create` with the same `attachmentId`, `ownerType` and `ownerId` (422 `validation`, numbered, fields `{attachmentId:'duplicate'}`). While approval is on, submit makes these checks and refuses with the error numbered as approval numbers it; with approval off the apply makes them. An archived or merged repository refuses the file at approval as it refuses an upload. While approval is on, submit also checks every operation's values as approval does before applying: the keys the person's route takes from its path must be strings, an existing record's `id` and `entry.upsert`'s `date` and `itemId` (`422 validation`, `id must be a string`), a create's `id` must be a name (see Names), a ticket's `itemId` is a string or null, and the payload must pass the operation's request model, the one the person's own route takes (`422 validation`, `Invalid proposed operation`, with the model's field errors). It refuses with the first failure numbered `Change N of M, ACTION:` and leaves the proposal a draft. What only the record itself can check (a date's calendar, a link's address, a person's email, a plan's step tree, a stale revision) still waits for approval. Each operation's keys and model are defined once, in `operations.py`.
Approval can be turned off: while `PATCH /settings {requireProposalApproval:false}` is in force, `submit` also approves in the same transaction. It applies every operation as the proposer and records `proposal.submit`, then `proposal.approve` by actor `{id:'automatic-approval',label:'Automatic approval',kind:'human'}`, and returns the proposal `approved`. Any failure (a stale revision, a validation error, a missing target) refuses the submit with that error's status, code and fields, a message starting `Not submitted:`, and nothing applied; the proposal stays a draft. Proposals already submitted when approval is turned off still wait for a human decision. Every proposal record carries `autoApproved`, true only for an automatic approval.
Proposal histories (schema v16). Approval records, in the same transaction, which work items and roadmaps each change was made to. A change counts toward the work item or roadmap it creates, changes, archives or recovers. It also counts toward the one holding the record it changes. A work item holds its tasks, scratchpad, links, files, agent chats, GitHub references, day entries and people ties. A roadmap holds its steps and their progress, notes and files, and its questions, decisions, notes, links, files, agent chats, GitHub references and people ties. A change also counts toward the roadmap it puts a work item on (`roadmapId` or `stepId`) or a sub-roadmap under (`parentId`). A ticket change counts toward the work item the ticket is linked to after it. A person, repository or resource alone counts toward neither. The v16 upgrade fills this in for proposals approved earlier, from their changes. A work item or roadmap an agent's proposal created is matched through its creation in history; one created by a proposal the person wrote is not. `GET /work-items/{id}/proposals?limit=50&offset=0` and `GET /roadmaps/{id}/proposals` page the approved proposals applied to that record. `GET /agents/{id}/proposals` pages everything an agent identity proposed, under any of its credentials and in every status (see Agent registry). All three return `{items,total}`, the latest first: by when each was applied for a record, by when each was created for an agent. Each item is `{number,id,title,status,autoApproved,actorLabel,agentId,createdAt,submittedAt,appliedAt,updatedAt,operationCount}`. `number` is its place in the sequence, 1 the first, and stays the same on every page. `agentId` is the proposer's identity, null for one the person wrote. `appliedAt` is set once approved. A record's items also carry `changes [{number,action}]`, the numbers and actions of its changes made to that record. An unknown record or agent returns 404 `not_found`; `limit` takes 1 to 200.

## Repository coordination

These records distinguish canonical repository/work relationships from self-reported agent activity. Repository catalog edits and item/chat `repositoryIds` are canonical: agents submit proposals and a human reviews them. Agents may register repositories (`POST /repositories/ensure`, or `repositoryUrl` in a participation context), which stay unreviewed until the person confirms or edits them. Agent routes permit catalog reads, registration, writes to the caller's own coordination records, and tracking the chat the caller registered with on work items and roadmaps. The credential authenticates the caller; `externalChatId`, local paths, branches, and run labels are provenance only. Worklog stores repository addresses and reported paths as metadata. The optional address accepts HTTP(S), SSH URLs, and Git SSH addresses such as `git@github.com:org/repo.git`.

All lists below return `{items,total,limit,offset}` with `limit=50` (maximum 200), `offset=0`. Creation and transition POSTs require `Idempotency-Key`; coordination PATCH accepts it too. The CLI requires a caller-supplied `--request-id` for every coordination write. Retry an uncertain result with the same key, route, and payload; select a new key for a new operation. Writes retain bearer redaction, literal-loopback transport, disabled proxies, and redirect refusal.

* `GET /repositories?archived=false&q=` (true lists archived only); `GET /repositories/{id}`: canonical catalog reads. The detail also carries the `people` tied to the repository (see People and links). Every repository record a route returns carries `discussionId`, its own discussion (schema v22), which registering a repository by any route opens and recovering one that has none opens; history events keep the record without it. Human `POST /repositories {name,url?,description?}`, `PATCH /repositories/{id} {revision,name?,url?,description?}`, and `POST /repositories/{id}/archive|recover {revision}` manage the catalog. Referenced archived records remain historical context.
* A record's `url` is the address as given; `remoteIdentity` keys its remote: host plus path, lowercased, without scheme, user, port, `.git` or trailing `/`. HTTPS, `ssh://` and `git@host:path` forms of one remote share it, and Azure DevOps' `dev.azure.com/{org}/{project}/_git/{repo}`, `{org}.visualstudio.com/[DefaultCollection/]{project}/_git/{repo}` and `ssh.dev.azure.com:v3/{org}/{project}/{repo}` all key as `dev.azure.com/{org}/{project}/_git/{repo}`. One record holds each remote: `POST /repositories` (and an approved `repository.create`) returns `{...record, created:true}` for a new record, or the record already holding the remote with `created:false` and no change. A remote held only by an archived record returns 409 `repository_archived` with `fields.repositoryId`; recover that record instead. A `PATCH` that moves `url` onto another record's remote returns 409 `repository_duplicate`. An HTTP(S) user name is dropped from `url`; a password is refused. Version 6 keeps records that already shared a remote before it and sets `duplicateOf` on all but the oldest active one; such a record keeps its links and reports, and when the record it points to moves to another remote, the oldest remaining duplicate takes its place.
* `POST /repositories/ensure {url,name?,description?}` (agents and the person; requires `Idempotency-Key`) registers a remote or returns the record that holds it, as `{...record,created}`. A new record's `name` defaults to the address's last path segment. It records `registeredBy {kind:'agent'|'human',label,agentId}`, the agent named by its identity (which outlives the credential), and `reviewed`: false for an agent's registration until the person confirms or edits it, true otherwise. A remote held only by an archived record returns 409 `repository_archived`. While `GET /settings` shows `agentRepositoryRegistration:false` (set with `PATCH /settings {agentRepositoryRegistration}`), an agent's ensure of an unregistered remote returns 403 `repository_registration_off`, and known remotes still resolve. Human-only `POST /repositories/{id}/confirm {revision}` marks a registration reviewed (no change when it already is); any human `PATCH` or approved `repository.update` does too. Records created by the person or by an approved proposal are reviewed from the start; version 7 takes existing records' registrants from their creation events.
* `GET /repositories/resolve?url=` returns `{url,remoteIdentity,repository}`: the address as it would be stored, its key, and the record registering it would link to (`null` when it would add one); an archived `repository` means registering is refused. An invalid address returns 422.
* Human-only `POST /repositories/{id}/merge {revision,intoId,intoRevision}` merges record `{id}` into `intoId`, checking both revisions. Work, chat and ticket links, people's ties, discussion tags (the merged record's own discussion becomes one tagged with the survivor), reported participation contexts, update feeds and attached files (archived ones included) move to the survivor (an owner or person already linked to it keeps one link, a person keeping the survivor's relationship); the records holding them keep their revisions, so agents keep working, and update snapshots keep the names they were posted with. The merged record is archived with `mergedInto` set, becomes read-only (409 `repository_merged` on edits, recovery and new contexts, with `fields.repositoryId` naming the survivor), and its remote answers with the survivor: registering it returns the survivor. Duplicates of the merged record, and records merged into it earlier, move to the survivor; a survivor that was its duplicate becomes canonical. Merging a record into itself returns 422; into an archived record, 409. Each record gets a `repository.merge` history event; the merged one's lists the moved counts. Agents cannot reach this route.
* `GET /agent-runs?includeEnded=false`; `GET /agent-runs/{id}`; `POST /agent-runs {clientRunKey,displayName,provider?,externalChatId?}`; `POST /agent-runs/{id}/end {revision}`. A run records a distinct execution context, attributable to its stable communication agent and originating credential. `clientRunKey` is stable within the originating credential. A registered identity's run that omits `externalChatId` reports the `chatId` the identity registered with. Ending is explicit.
* `GET /participations?repositoryId=&itemId=&runId=&includeReleased=false`; `GET /participations/{id}`. `POST /participations {runId,itemId?:null,description?:'',contexts:[{repositoryId,checkoutPath?,worktreePath?,branch?}]}` reports work across one or more repositories without requiring a work item. A context may give `repositoryUrl` instead of `repositoryId`: the remote is ensured as above in the same transaction, so a refusal leaves no participation, and the stored context names the record's ID. A supplied work item must exist. `description` describes current activity (maximum 2,000 characters). `PATCH /participations/{id} {revision,itemId?,description?,contexts?}` replaces supplied fields; `itemId:null` removes the optional work link. When participation (created, updated, checked in or rejoined) names a work item and its run's `externalChatId` is the `chatId` its registered identity registered with, Worklog tracks that chat on the item in the same transaction, unless a chat with exactly that `chatId` is already tracked there, archived included. The new record is an agent chat owned by the item, titled after the run's `displayName`, with the run's `provider`. The person asked for this to happen without a proposal; the chat's history records `chat.create` by the reporting credential. A chat ID that a run only names, on any credential, stays provenance and is never tracked this way, so an agent cannot fill work with chats.
* Agent only: `POST /chats/track {ownerType:'item'|'roadmap',ownerId,stepIds?:[],title?,provider?:'',model?:''}` (requires `Idempotency-Key`) tracks the chat the caller's identity registered with on that work item or roadmap, and on steps of the roadmap, without a proposal, and returns the agent chat with `created`. The chat's ID always comes from the identity: a request naming `chatId` is refused (422), a credential issued in Settings, which registered no chat, gets `403 agent_scope`, and a person's session `403 forbidden`. Unknown work is `404 not_found` and archived work `409 archived`. With no chat of exactly that `chatId` tracked there, it creates one, recorded as `chat.create` by the calling credential: titled `title`, else the identity's label, with `provider`, `model` and `stepIds` checked as on `POST /chats` (steps of that roadmap only, none retired). With one tracked there, the active one first, it adds the `stepIds` the chat lacks, recorded as `chat.update` with a `chat.assign` in each step's history, and changes nothing else; naming none changes nothing, and `created` is false. What the person decided stays: when the only one tracked there is archived, the request gets `409 archived` with `fields.id`, and a step an update took the chat off (`chat.unassign` in the step's history) `403 forbidden` with `fields.stepIds`, refusing the whole request. Like delivery, this trusts the chat ID an identity gave when it registered, which Worklog cannot verify: an identity registered with another chat's ID tracks that chat and can add steps to its records there.
* `POST /participations/{id}/check-in|release|rejoin {revision}` explicitly refreshes reported activity, releases participation, or rejoins. Current revisions protect against lost updates. Multiple participations may overlap: these records are advisory and never block edits or confer operating authority. Two hours without reported activity changes display staleness only; it does not release participation, expire authority, or prove process liveness. No periodic heartbeat or automatic agent wake-up is required.
* `POST /participations/{id}/updates {kind:'update'|'blocker'|'handoff',text}` appends an immutable update. `GET /coordination-updates?participationId=&repositoryId=&itemId=` returns persisted updates scoped to their original context snapshots. Later participation edits do not move past updates to different repositories or work items. `blocker` and `handoff` classify information; they do not enforce a dependency or transfer ownership.
* `GET /context?date=&repositoryId=&itemId=` includes repository/run/participation/update summaries, the open, doing and blocked `tickets`, and the active `resources` as list items (without their text), with optional repository and work filters; the resources are not filtered by repository or work. Existing daily context remains available when filters are omitted.

The CLI exposes `agent repositories list|show|ensure`, `agent runs start|end|show|list`, `agent participation start|update|check-in|release|rejoin|show|list`, `agent updates post|list`, and `agent chats track --item ID | --roadmap ID [--step ID]... [--title] [--provider] [--model] --request-id KEY`, which sends `POST /chats/track` and never a chat ID. List reads accept `--limit`/`--offset`; catalog lists accept `--archived`/`--q`, run lists `--include-ended`, participation lists `--repo`/`--item`/`--run`/`--include-released`, and update lists `--repo`/`--item`/`--participation`. `agent context` accepts `--repo` and `--item` alongside `--date`. `repositories ensure --remote URL|--checkout PATH [--name] [--description] --request-id KEY` registers a remote. `participation start --checkout PATH` (repeatable, with or without `--repo`) runs `git -C PATH remote get-url origin` and `git rev-parse` to report `{repositoryUrl,branch,checkoutPath}`, or `worktreePath` plus the main `checkoutPath` for a linked worktree; a folder without an `origin` fails before any request. Other catalog mutations (edit, archive, recover, confirm, merge) are intentionally absent from the agent client allowlist.

For detailed local context, pass a JSON file to `participation start --file` (or `-` for stdin):

```json
{"runId":"RUN_UUID","contexts":[{"repositoryId":"REPOSITORY_UUID","checkoutPath":"C:/Projects/example","worktreePath":"C:/Worktrees/example-task","branch":"codex/task"}]}
```

Use `participation update PARTICIPATION_ID --revision N --file FILE --request-id KEY` with `{itemId,description,contexts}` as needed; omitted fields stay unchanged. To change just the activity description, use `--description TEXT` instead of `--file`. `updates post --participation ID --file FILE --request-id KEY` accepts `{kind,text}`; `--text` defaults to `kind:update` and permits `--kind blocker|handoff`. Posting an update advances the participation revision: read the current participation before its next revision-checked write. Canonical proposals support `repository.create|update|archive|recover` and `repositoryIds` on item/chat create/update operations; approval remains atomic and revision checked. A `repository.create` for an already registered remote applies as a link to that record, so overlapping proposals from parallel agents all apply; stale revisions and invalid operations still roll back the whole proposal. Repository associations use IDs; changing a legacy chat `repos` label does not create or link catalog entries.

## Agent registry

Browser session only: an agent credential gets `403 agent_scope`, because an agent's record joins the tracked chats it reported. The registry writes nothing. Each agent is a stable communication identity (one per credential family, kept across rotation); its record is gathered from the runs, participation, status updates, discussion messages and owned roles it already wrote, so it cannot drift from them. Reported chat IDs, paths and branches remain provenance.

* `GET /agents?limit=50&offset=0&q=` lists `{id,label,active,createdAt,lastActivityAt,providers,openRuns,runCount,messageCount,working,roles}`, agents with an active credential first, then the most recently active; `q` (at most 200 characters) keeps those whose label holds it, ignoring case. `lastActivityAt` is the latest run start, participation report, status update or message by the agent; a human ending its runs or revoking its credential does not count. `working` holds open participation `{participationId,runId,runName,description,lastSeenAt,stale,item?,roadmap?,contexts}` (an item's roadmap is its step's roadmap, else its own), and `roles` the responsibility roles it owns `{id,label,contextType,contextId,contextTitle,roadmap?,updatedAt}`.
* `GET /agents/{id}` adds `credentials [{id,label,createdAt,revoked,registeredBy,chatId}]` (`chatId` is the chat a registered identity works in, null when issued in Settings), `runs {items,total}` (latest 200, each with the tracked `chats` carrying its `externalChatId`), and the records its work ties it to (the agent page's "From its work"; the ties set by the person or the agent are `GET /agent-links`): `workItems`, `roadmaps`, `repositories` and `chats`, each `{items,total}` with at most 200 items, current ties first and then the most recent. Every tie carries `via`, the reasons it exists (`participation`, `role`, `update`, `message`, `run`, `confirmed`, `chat`), `current` (open participation, an owned role, or a tracked chat reported by an open run) and `lastAt`. Messages tie the agent to their discussion's item, roadmap and step contexts; a tracked chat whose chat ID the agent reported in a run or message, or where the person confirmed it (`confirmed`, never current), ties it to that chat's owner and catalog repositories; work on a roadmap's item also ties the roadmap; a step ties its roadmap.
* `GET /agents/{id}/activity?limit=50&offset=0` pages the agent's discussion messages `{kind:'message',id,createdAt,text,truncated,discussionId,discussionTitle,chatId,chats}` and status updates `{kind:'update',id,createdAt,text,truncated,updateKind,runName,participationId,item?,contexts}` newest first. `text` is the first 1,000 characters; `contexts` is the snapshot kept when the update was posted.
* `GET /agents/{id}/proposals?limit=50&offset=0` pages the agent's proposals, the latest it made first, numbered in the order it made them (see Proposals).
* `GET /roadmaps/{id}/agents` lists who works on a roadmap now, `{items:[{kind:'agent'|'chat',id,label,avatar,provider,model,ties,lastAt,stale}]}`, fresh work first and then the most recent; the Plan & progress outline shows it beside each step. Only current ties count: open participation in the roadmap's work items (an item's roadmap is its step's roadmap, else its own), roles agents own on the roadmap, its steps or its work items, and its tracked chats that are not archived. Finished work is left out: an agent counts only while it has an open run and an active credential, and a tracked chat only until the tool that keeps it archives it too (the Claude desktop app archives a session, Codex moves a thread to `archived_sessions`). Each tie is `{stepId,via:'participation'|'role'|'chat',item?,chat?,role?,lastAt,stale}`: participation and a work item's chat or role take the item's step, a roadmap's chat takes each step assigned to it, and work with no step, or on a retired one, has a null `stepId`. A tracked chat is listed under every agent whose open run reported its chat ID, and left out once every run that reported it has ended; one that no run reported is its own `kind:'chat'` entry, with its title as `label` and its provider and model. `stale` marks participation not reported for two hours, and a worker is `stale` when all its ties are. Agents have their `avatar`; a chat has none.

## Agent self-registration

An agent credential registers a separate identity for the agent holding it; see the [agent guide](AGENT-GUIDE.md) for the CLI. The registering credential is the only authority, and the new identity gets the same agent scope, nothing more. Neither route writes an idempotency receipt, since a receipt's request hash would derive from the token.

* `POST /agent-registrations {label,token,chatId,avatar?,directory?}` with an agent bearer creates a credential whose token is the caller-generated `token` and binds it to a new identity working in chat `chatId`: a Claude Code session ID, a Claude desktop `local_…` ID or a Codex thread ID, 1–500 bytes without spaces or control characters, trimmed. `directory` (schema v18) is the absolute directory the agent works in, as `worklog agent register` sends its current one: a Windows (`C:\…`, `\\server\share\…`) or POSIX (`/…`) path of up to 2,000 bytes, trimmed, whose every character shows as itself: no control, formatting (such as a bidirectional override or a zero-width space) or line or paragraph separator character, while spaces of any kind are kept; anything else is `422 validation` naming `directory` in its fields. Review shows it beside the identity's proposals (`actorDirectory`); omitted, it stays null. The `credential.register` event records the chat and the directory. The identity's runs report that chat unless they name another, work they report tracks it (see participation above), and `POST /chats/track` tracks it on the work it names. The token is 43–200 characters of `A-Z`, `a-z`, `0-9`, `-`, `_`; generate it from at least 32 random bytes, for example with `secrets.token_urlsafe(32)`. A token with fewer than 10 distinct characters is refused as `422`. The label `You`, which names the person, is refused too. It returns `{id,agentId,label,avatar,chatId,registeredBy:{id,label},directory}`, never the token; `registeredBy` is the registering agent's identity. Only the token's SHA-256 is stored. The token is the idempotency key: repeating the request with an active registered token and the same `chatId` returns that registration unchanged, with the directory it first recorded whatever `directory` the repeat sends; another `chatId` is `409 chat_mismatch` (an identity works in one chat; register another for another chat), a revoked token is `409 token_revoked`, and the token of a credential issued in Settings is `409 token_in_use`. `GET /settings` credentials carry `chatId` too. A person's session gets `403 agent_scope` and a taken avatar `409 avatar_in_use`. When 200 registered identities are active, or agents registered 200 since local midnight, the request gets `429 agent_limit`. Credentials issued in Settings never count.
* `POST /agent-registrations/retire {}` with a registered credential's bearer revokes that credential, ends its open runs and releases their participation with reason `credential_retired`. It also revokes every identity it registered, as below. It returns `{id,agentId,retired:true,registeredRevoked}`. A credential issued in Settings, or a person's session, gets `403 agent_scope`; the retired token then gets `401`.
* `POST /credentials/{id}/revoke` also revokes every active credential of the identities registered by that credential's identity, directly or through the ones they registered. It ends their open runs (`credential_revoked`) and returns `{ok:true,registeredRevoked}`. Rotation keeps them, because it keeps the identity.
* The `credential.register`, `credential.retire` and `credential.revoke` events record each change; a revoke that followed from another carries `via`, the credential revoked first. Settings `credentials` and `GET /agents/{id}` `credentials` carry `registeredBy {id,label}`, or `null` for a credential issued in Settings. Settings `credentials` also carry `registeredActive`, the number of active identities that revoking the credential would revoke.

## Messages to a chat's agents

The person writes into a tracked chat; agents receive. Recipients are fixed when a message is sent: every open run whose `externalChatId` equals the chat's `chatId` exactly, on a credential that is not revoked, of an identity bound to that chat. An identity is bound to the chat it registered with, and to each chat where the person confirmed it (since schema v13). Any credential's run can report any chat ID, so another run reporting it is only a claim: it is listed as unconfirmed and receives nothing. Writes require `Idempotency-Key`.

* Browser session only (an agent credential gets `403 agent_scope`, as it does for `GET /history` of a message): `GET /chats/{id}/messages?limit=50&offset=0` returns `{chat:{id,chatId,archived},recipients,unconfirmed,items,total,limit,offset}`. `recipients` lists `{runId,runName,provider,startedAt,agentId,agentLabel,avatar,registeredBy,binding}` a message sent now would reach, with `binding` `'registered'` or `'confirmed'`. `unconfirmed` lists the claims, `{runId,runName,provider,startedAt,agentId,agentLabel,avatar,registeredBy}`. `registeredBy` is the `{id,label}` of the identity that registered the agent's identity, and `null` for a credential issued in Settings; agents choose their own labels, so this is what tells two apart. Both lists are empty for an archived chat. `items` are newest first: `{id,chatId,text,authorId,authorLabel,createdAt,deliveries}`, each delivery `{runId,runName,agentId,agentLabel,avatar,status:'pending'|'delivered'|'expired',reason,expiresAt,deliveredAt,expiredAt}`.
* `POST /chats/{id}/messages {text}` (Markdown, at most 1,000,000 UTF-8 bytes) returns the message with its deliveries. `409 chat_archived` refuses an archived chat, which stays archived; `409 no_recipients` refuses a chat with no open run of a bound identity, and its message says so when only claims are left. Neither stores anything.
* `POST /chats/{id}/confirmations {agentId}` confirms that the identity works in the chat: what the person writes into it from then on reaches that identity's open runs on the chat, on every record that tracks the same `chatId`, and through credential rotation. `POST /chats/{id}/confirmations/remove {agentId}` removes the confirmation and ends what still waits for that identity in the chat (`unconfirmed`). Both return `{chat:{id,chatId},agentId,binding}`, with `binding` `'registered'`, `'confirmed'` or `null`, and change nothing for an identity bound by registration. `404 not_found` refuses a missing chat or identity, and `409 chat_archived` an archived chat. They write `chat.confirm` and `chat.unconfirm` to the chat's history.
* `POST /chat-confirmations {chatId,agentId}` and `POST /chat-confirmations/remove {chatId,agentId}` do the same by a chat's ID, whether or not a record tracks it yet, such as a Claude Code session running on this machine. `chatId` (at most 500 characters) is the ID as the identity's runs report it. They return `{chatId,agentId,binding}`, refuse an unknown identity with `404 not_found`, and write `chat.confirm` and `chat.unconfirm` to the identity's history. Agents get `403 agent_scope`.
* Agent only: `POST /inbox/receive {chatId?}` hands the caller's credential its waiting messages, oldest first, and marks them delivered, so each arrives once; two open runs on one chat still get one copy, `{id,text,authorKind:'human',authorId,authorLabel,sentAt,chat:{id,chatId,title},runIds}`. `chatId` limits it to runs that reported that chat ID. A run must still be open and tied to the chat, and its identity bound to it, when a message is handed out. Retrying an uncertain result with the same key returns the same messages, and nothing that request did not already receive; an empty result keeps no receipt. The CLI is `agent inbox [--chat CHAT_ID] [--request-id KEY]`.

A pending delivery expires, with `reason`, when its run ends (`run_ended`, or `human_closed` when you end it), its credential is revoked or rotated (`credential_revoked`, `credential_rotated`), its agent retires (`credential_retired`), its chat is archived (`chat_archived`) or its `chatId` is changed (`chat_changed`), the person removes its identity's confirmation (`unconfirmed`, as does the v13 upgrade for an identity bound to no chat it was sent to), or a restore ends every run (`restore`). Recovering the chat afterwards does not revive it. A delivery still pending at `expiresAt`, two hours after sending, reads as expired with reason `not_picked_up` and is never handed out. No route recovers a chat, reopens a run, or touches a provider session.

## Tickets

Tickets are shared records the person and agents write directly; agents may also file and change them by proposal (`ticket.create`, `ticket.update`; see Proposals). Every write runs as the caller's stable communication identity (the person is `local-user`), so authorship and retry receipts survive a token rotation, and a credential revoked meanwhile is refused inside the write lock. Agents may `POST /tickets`, `PATCH /tickets/{ref}` and `POST /tickets/{ref}/comments`, and read every ticket; archive and recover are the person's alone (`403 agent_scope`). `{ref}` is the ticket's UUID, its key `T-12` (any case) or its number `12`. Numbers are one sequence, allocated in the write transaction and never reused; a restore returns them to the restored data, so later tickets can take numbers that ones created after the backup had.

* A ticket is `{id,number,key,title,description,resolution,truncated,kind:'bug'|'incident'|'task',priority:'low'|'normal'|'high'|'urgent',status:'open'|'doing'|'blocked'|'done',labels,repositoryIds,itemId,item:{id,title,status,archived}|null,assigneeId,assignee:{id,label,kind,avatar,active}|null,author:{id,label,kind,avatar},commentCount,archived,revision,createdAt,updatedAt,closedAt,lastActivityAt}`. Titles are required, up to 1,000 UTF-8 bytes; `description`, `resolution` and comment text are Markdown up to 100,000.
* `GET /tickets?status=active|open|doing|blocked|done|all&q=&kind=&priority=&label=&repositoryId=&itemId=&assigneeId=&archived=false&sort=priority|recent&limit=50&offset=0` returns `{items,total,limit,offset}` (limit at most 200). `active` (the default) is open, doing and blocked. `q` matches words in titles, descriptions, resolutions, kinds, labels and comments; `assigneeId` takes an identity, `local-user` or `none`; `archived=true` lists archived tickets only. `priority` sorts urgent first, then by latest activity; `recent` by latest activity alone. List items carry the first 1,000 characters of `description` and `resolution`, with `truncated` when either was cut.
* `GET /tickets/{ref}?comments=200` adds the full text, `comments {items,total}` (the latest `comments` comments, 1 to 1,000, oldest first, each `{id,ticketId,text,createdAt,author}`) and `history`, the latest 100 changes newest first as `{id,kind,actorId,actorLabel,actorKind,createdAt}`. Each change's before and after records repeat the whole ticket, so they are left out here; `GET /history?entityId=` returns them.
* `POST /tickets {title,description?,kind?='bug',priority?='normal',status?='open',resolution?,labels?,repositoryIds?,itemId?,assigneeId?}` requires `Idempotency-Key`. `PATCH /tickets/{ref} {revision,...the same fields}` replaces the fields it supplies; `labels` and `repositoryIds` replace the whole set, and `itemId:null` or `assigneeId:null` clears that link. `Idempotency-Key` is optional on PATCH.
* `done` needs a non-blank resolution (`422 fields {resolution:'required'}`), whether set on creation, by a change, or by the resolution a ticket already has. Moving to `done` sets `closedAt`; leaving it clears `closedAt` and keeps the resolution.
* Labels are at most 20, lower-cased, each `[a-z0-9][a-z0-9._-]{0,49}`. A new repository link needs an active catalog repository (`422 repository_unavailable`), a new work item link an active item (`404`, or `409 archived`), and a new assignee the person or an identity with a live credential (`422 assignee_unavailable`). Existing links stay when their target is archived or revoked later.
* `POST /tickets/{ref}/comments {text}` requires `Idempotency-Key` and appends an immutable comment. It moves `lastActivityAt` but not the ticket's `revision`, so a comment never makes an edit conflict.
* Person only: `POST /tickets/{ref}/archive|recover {revision}`. An archived ticket refuses changes and comments (`409 ticket_archived`) and leaves default lists and search, as do its comments.
* History records `ticket.create`, `ticket.update`, `ticket.close`, `ticket.reopen`, `ticket.comment`, `ticket.archive` and `ticket.recover` on the ticket's ID, with full before and after records. Search indexes a ticket as `ticket` and each comment as `ticket_comment`, both titled with the key and routing to `routeType:'tickets'` and the ticket's ID.

The CLI exposes `agent tickets list|show|create|update|close|comment`. `list` takes `--status`, `--q`, `--kind`, `--priority`, `--label`, `--repo`, `--item`, `--assignee me|none|ID`, `--sort`, `--archived`, `--limit` and `--offset`; `show` takes `--comments`. `create` and `update` take `--title`, `--description`, `--kind`, `--priority`, `--status`, `--resolution`, repeated `--label` and `--repo`, `--item`, `--assign me|none|ID` and `--file` (`-` reads standard input), and `update` also `--no-item`, `--no-labels` and `--no-repos`. `close` sets `done` with `--resolution`, and `comment` takes `--text` or `--file`. `me` resolves through `GET /discussions/participants` to the caller's identity. Every write sends an `Idempotency-Key`: the `--request-id` given, or a fresh one that an uncertain result names for the retry. Archive and recover are absent from the agent client allowlist.

## Resources

Resources are reference pages the person writes for themselves and their agents. The person creates, edits, archives and recovers them; agents read them with the same GET routes and the CLI, and change them only by proposal (`resource.create`, `resource.update`, `resource.archive`, `resource.recover`; see Proposals), applied as the proposing agent once approved, or on submit while approval is off. Every direct agent write is refused (`403 agent_scope`), and the service's own write methods refuse a non-person actor too: only an applied proposal's change, which `WorkService.apply(..., proposed=True)` routes, reaches a page as an agent.

* A list item is `{id,title,summary,archived,revision,createdAt,updatedAt}`; a whole page adds `body`. `title` is required, up to 1,000 UTF-8 bytes, and trimmed; `summary`, what the page is for, is up to 2,000 and kept as typed; `body` is Markdown up to 1,000,000.
* `GET /resources?q=&archived=false&limit=50&offset=0` returns `{items,total,limit,offset}` (limit at most 200) by title, case-insensitive, without the pages' text. `q` matches words, as prefixes, in titles, summaries and text; `archived=true` lists archived pages only.
* `GET /resources/{id}` returns the whole page and `history`, the latest 100 changes newest first as `{id,kind,actorId,actorLabel,actorKind,createdAt}`; `GET /history?entityId=` has each change's full before and after records.
* `POST /resources {title,summary?,body?}` requires `Idempotency-Key`. `PATCH /resources/{id} {revision,title?,summary?,body?}` replaces the fields it supplies. An archived page refuses changes (`409 archived`) until recovered.
* `POST /resources/{id}/archive|recover {revision}`. An archived page leaves default lists, `context` and search; the person and agents can still read it by ID, and `GET /history?entityId=` keeps every earlier version of a page.
* History records `resource.create`, `resource.update`, `resource.archive` and `resource.recover`. Search indexes each page as `resource`, its summary and text as the body, routing to `routeType:'resources'` and the page's ID.

The CLI exposes `agent resources list|show`, read-only: `list` takes `--q`, `--archived`, `--limit` and `--offset`, and `show ID` reads one page. The agent client allowlist has no resource write route.

Schema v9 adds the `resources` table; an upgrade leaves it empty.

## Releases

A release is what ships together: dated (`releaseDate`, a YYYY-MM-DD day) or not dated (`null`), and `planned` until it is `released` or `cancelled`. It holds work items, roadmaps, roadmap steps and GitHub references by ID, and its checks say who needs to know (`notify`), what to test (`test`) and what to prepare first (`prepare`). Every write runs through `WorkService.apply`. Agents read releases with the same GET routes and the CLI, and change them only by proposal: `release.create`, `release.update`, `release.add`, `release.remove`, `check.create` and `check.update`, which take the person's route payloads and may name what a create makes (`releaseId` takes a release's name). Archive and recover stay the person's, and every direct agent write is refused (`403 agent_scope`). An applied release change counts toward no work item's or roadmap's proposal history.

* A release is `{id,title,description,releaseDate,status,archived,revision,createdAt,updatedAt}`; reads add `pastDue`, true for a planned, unarchived release whose date is before today in the person's timezone. `title` is required, up to 1,000 UTF-8 bytes, and trimmed; `description` is Markdown up to 1,000,000. The database holds only real days or null in `release_date` and `due_date`, by CHECK, since past-due flags and the list's order compare them as text.
* `GET /releases?status=planned&archived=false&q=&targetType=&targetId=&limit=50&offset=0` returns `{items,total,limit,offset}` (limit at most 200), each item with `counts:{items,itemsDone,notify,test,prepare,pastDue}`: its unarchived work items and the done ones, its open checks of each kind, and open checks past due. `status` is `planned`, `released`, `cancelled` or `all`. Planned releases come first, soonest first; then the others, latest first; not dated ones end each group. `q` matches words, as prefixes, in titles, descriptions and the releases' checks. `targetType` (`item`, `roadmap`, `step` or `github`) with `targetId` keeps the releases that hold that record.
* `GET /releases/{id}` adds `items` (`{id,title,status,archived,addedAt}`), `roadmaps` (with `steps` and `stepsDone`, its leaf steps as its progress bar counts them), `steps` (with the derived `status`, `retired`, `roadmapId`, `roadmapTitle` and `roadmapArchived`), `changes`, `checks` and `history`. `changes` are the GitHub references the release holds, archived ones included, and the active ones owned by the work items and roadmaps it holds, once each: `{id,kind,url,reference,title,ownerType,ownerId,ownerTitle,chatId,chatTitle,provider,model,direct,archived,createdAt}`, where `chatId` is the tracked chat that made the change and `direct` says the release holds it itself. `checks` holds every check, archived ones too, by due date (not dated last), then as added. `history` is the latest 100 changes to the release and its checks, newest first, as `{id,entityId,kind,actorId,actorLabel,actorKind,createdAt}`; `GET /history?entityId=` has each one's records.
* `POST /releases {title,description?,releaseDate?,status?}` requires `Idempotency-Key`. `PATCH /releases/{id} {revision,title?,description?,releaseDate?,status?}` replaces the fields it supplies; an explicit `null` `releaseDate` makes the release not dated. `POST /releases/{id}/archive|recover {revision}`. An archived release refuses every change to itself, its contents and its checks (`409 archived`) until recovered.
* `POST /release-contents {releaseId,targetType,targetId}` holds a record and `POST /release-contents/remove` with the same body stops holding it; each returns `{releaseId,targetType,targetId,changed}`, and holding a record already held, or removing one not held, changes nothing and records nothing. Neither changes a revision. A missing record is `404 not_found`; an archived work item, roadmap or GitHub reference, or a step of an archived roadmap, is `409 archived`; a retired step is `409 conflict`.
* A check is `{id,releaseId,kind,text,details,personId,personName,personArchived,dueDate,status,archived,revision,createdAt,updatedAt}`; reads add `pastDue`, true for a check not done and not archived whose due date is before today. `POST /release-checks {releaseId,kind,text,details?,personId?,dueDate?,status?}` requires `Idempotency-Key`; `GET /release-checks/{id}`; `PATCH /release-checks/{id} {revision,kind?,text?,details?,personId?,dueDate?,status?}`, where an explicit `null` clears the person or the due date; `POST /release-checks/{id}/archive|recover {revision}`. `status` takes a work item's states. `text` is required, up to 2,000 bytes; `details` is Markdown up to 100,000. A person newly named must exist and be active (`404 not_found`); one already named stays when archived later.
* History records `release.create`, `release.update`, `release.archive`, `release.recover`, `release.add` and `release.remove` on the release, and `check.create`, `check.update`, `check.archive` and `check.recover` on the check. Search indexes each release as `release` and each check as `release_check`, both owned by the release and routing to `routeType:'releases'` and its ID; archiving a release hides its checks at query time, and each check keeps its own archive flag.

The CLI exposes `agent releases list|show`, read-only: `list` takes `--status`, `--q`, `--item`, `--archived`, `--limit` and `--offset`, and `show ID` reads one release. The agent client allowlist has no release write route. `GET /context` includes `releases`: upcoming releases with their counts, or with `itemId` those that hold the item.

Schema v19 adds the `releases`, `release_contents` and `release_checks` tables; an upgrade leaves them empty.

## Reminders

Reminders are the person's: what to come back to on a day, or at a time on it. The person and agents set, change, snooze, complete and reopen them directly; archive and recover are the person's alone (`403 agent_scope` for an agent, and the service refuses any other actor too). As with tickets, every write runs as the caller's stable communication identity (the person is `local-user`), so authorship and retry receipts survive a token rotation, and a credential revoked meanwhile is refused inside the write lock. No proposal operation names a reminder.

* A list item is `{id,title,date,time,state,due,overdue,target,author,archived,revision,createdAt,updatedAt,doneAt}`; a whole reminder adds `notes`. `date` is YYYY-MM-DD and `time` HH:MM on a 24-hour clock, or null for all day, both by the clock of the Worklog timezone setting. `state` is `open` or `done`, and `doneAt` is set while it is done. `due` is worked out as it is read: open, and dated before today, or today with its time (00:00 when all day) at or before now. `overdue` is open and dated before today. `target` is null or `{type,id,title,archived}`, read as the record stands now; a ticket's title starts with its key. `author` is `{id,label,kind,avatar}`. `title` is required, up to 1,000 UTF-8 bytes, and trimmed; `notes` is Markdown up to 100,000.
* `GET /reminders?state=open|due|upcoming|done|all&date=&until=&targetType=&targetId=&q=&archived=false&limit=50&offset=0` returns `{items,total,limit,offset}` (limit at most 200), without notes. `open` (the default) is every open reminder, `due` the open ones due now and `upcoming` the open ones not due yet. Open ones come first, by date, all-day before timed, then by time; done ones follow, the latest done first. `date` keeps those due on that day and `until` those due on or before it. `targetType` (`item`, `ticket`, `roadmap`, `person`, `repository` or `chat`) and `targetId` together keep those that name one record; a ticket can be named by its key. `q` matches words, as prefixes, in titles and notes; `archived=true` lists archived reminders only.
* `GET /reminders/{id}` returns the whole reminder and `history`, the latest 100 changes newest first as `{id,kind,actorId,actorLabel,actorKind,createdAt}`; `GET /history?entityId=` has each change's full before and after records.
* `POST /reminders {title,date,time?,notes?,targetType?,targetId?}` requires `Idempotency-Key`. `PATCH /reminders/{id} {revision,title?,notes?,date?,time?,state?,targetType?,targetId?}` replaces the fields it supplies: `time:null` makes it all day, `targetType:null,targetId:null` stops naming a record, and `state` sets or clears `doneAt`. A record named anew must exist (`404 not_found`) and be active (`409 archived`); a record already named stays named after it is archived. An archived reminder refuses changes (`409 archived`). `Idempotency-Key` is optional on PATCH.
* Person only: `POST /reminders/{id}/archive|recover {revision}`. An archived reminder leaves default lists, Today, the sidebar's count and search.
* A repository merge moves the reminders that name the source to the survivor without changing their revisions; the merge event's `moved` counts them as `reminders`.
* History records `reminder.create`, `reminder.update`, `reminder.done`, `reminder.reopen`, `reminder.archive` and `reminder.recover`. Search indexes each reminder as `reminder`, with its notes as the body, routing to `routeType:'reminders'` and the reminder's ID.

The CLI exposes `agent reminders list|show|add|update|done|reopen`. `list` takes `--state`, `--date`, `--until`, one of `--item`, `--ticket`, `--roadmap`, `--person`, `--repository` or `--chat`, `--q`, `--archived`, `--limit` and `--offset`. `add` takes `--title`, `--on`, `--at`, `--notes` and a record option; `update` takes `--revision` and the same options, plus `--all-day` and `--unlink`; `done` and `reopen` take `--revision`. Every write sends an `Idempotency-Key`: the `--request-id` given, or a fresh one that an uncertain result names for the retry. Archive and recover are absent from the agent client allowlist.

Schema v20 adds the `reminders` table; an upgrade leaves it empty.

Schema v21 adds `days.reflection_revision`; an upgrade starts it at each day's `revision`.

## Settings and administration
GET /settings -> {timezone,today,requireProposalApproval,storage:{databaseBytes,backupBytes,warning},backups:[{name,size,createdAt}],credentials:[{id,label,createdAt,revoked,agentId,registeredBy,registeredActive}],version}. PATCH /settings {timezone?,requireProposalApproval?} changes only the fields supplied and returns the settings; each change records a `settings.timezone` or `settings.requireProposalApproval` event. `requireProposalApproval` is a strict boolean, true when never set; false makes submitting a proposal apply it (see Proposals). POST /credentials {label,avatar?} -> {id,agentId,label,avatar,token} once; without `avatar` a new identity draws the least-used one, preferring a colour no active agent shows. Settings `agents` include `avatar`. POST /credentials/{id}/revoke {}. POST /backups {} -> metadata. GET /export -> zip download. GET /search?q=&archived=false&limit=50&offset=0&type= -> {items:[{id,type,title,snippet,ownerId?,routeType,routeId}],total}; `type`, repeatable, narrows the results to those indexed kinds (`item`, `step`, `roadmap`, `note`, `attachment`, `link`, `chat`, `github`, `question`, `decision`, `person`, `ticket`, `ticket_comment`, `discussion`, `discussion_message`, `resource`, `release`, `release_check`, `reminder`), and any other value is 422.
Settings, credentials (issue, rotate and revoke), backups and the export are the person's twice over: `policy.ROUTES` gives them the person's scope, and each route also declares `app.person_only`, which refuses every other caller with `403 agent_scope` even if the table let it in. `test_person_only.py` pins which routes declare it.
